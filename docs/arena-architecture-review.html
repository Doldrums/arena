Arena — платформа.
Фреймворки — её участники.

Arena хранит задачи и окружения, регистрирует участников, запускает эксперименты и показывает результаты. Борду строим на основе текущего dashboard SCiEL. Сам SCiEL подключается на тех же условиях, что ShinkaEvolve и DGM.

Граница платформы и участников

Arena владеет экспериментом

Каталог, версии задач и окружений, очередь, бюджеты, исполнение, проверка, результаты и борда — части одной платформы.

Участник владеет алгоритмом

SCiEL, Shinka и DGM сами выбирают следующий шаг поиска. Arena запускает их целиком и предоставляет контракт проверки.

02 / UML Deployment diagram

Cloudflare управляет. Vast исполняет.

Предлагаю для v1 один Worker deployment с интерфейсом и API, D1 для состояния, R2 для файлов и одну Linux VM на Vast.ai. VM забирает задания исходящими HTTPS-запросами; публичный endpoint выполнения на Vast не нужен.

Control DBCloudflare D1.Регистрации, RunSpec, очередь, leases, состояния, индекс событий и расходов.
ArtifactsCloudflare R2.Код, пакеты, сырые журналы, checkpoints и результаты. Большие файлы — прямой upload по ограниченным signed URLs.
SupervisorPython daemon на Vast VM.Claim, heartbeat, контейнеры, лимиты и журнал до подтверждения доставки. Отдельные service credentials на worker; account-wide ключи ему не выдаём.
Participant / evaluatorРазные OCI-окружения по image digest.У участника нет control-plane credentials и права менять официальный evaluator. Кандидат исполняется с лимитами задачи.

Выбираем Vast VM с Docker. Она поддерживает отдельные контейнерные среды. Обычный Vast Docker instance сам является контейнером — это другое execution environment. Диск машины используем как кэш; подтверждённые результаты храним в R2.

Проверенные возможности: Workers Static AssetsWorkers limitsD1R2 uploadsVast VMs

Для одной VM достаточно транзакционной очереди в D1 и pull-протокола. Cloudflare Queues, Durable Objects, Kubernetes и автоматическую аренду флота машин в v1 не вводим.

03 / UML Sequence diagram

Репозитории подключаем через общий реестр

Подтверждено Только наша команда; добавление через PR. Предлагаю реестр в registry/ репозитория Arena. Источники задач и участников остаются в своих GitHub-репозиториях.

Предлагаемая структура

arena/                     # платформа
  web/                     # board из SCiEL
  api/                     # Cloudflare Worker
  worker/                  # Vast supervisor
  schemas/                 # контракты
  registry/tasks/          # регистрации
  registry/participants/

autoresearch-tasks/         # библиотека задач
sciel/                     # участник
arena-participants/        # адаптеры Shinka/DGM
                           # + pinned upstream

Что делает кнопка «Добавить»

Открывает шаблон PR в GitHub. После merge Arena читает manifest, строит окружение и выполняет conformance — проверку совместимости интерфейса.

Можно подключить одну задачу или коллекцию. Для Shinka/DGM достаточно adapter repo со ссылкой на upstream commit; менять исходный проект не обязательно.

GitHub App получает доступ только к выбранным репозиториям. Существующая приватная библиотека задач поддерживается.

Разделяем три статуса: версия прошла проверку совместимости; версия рекомендована командой; evaluator имеет определённый уровень научной проверки. Успешная сборка не подтверждает научную корректность.
Пример записи реестра

Предложение схемы; организация и commit — placeholders.

kind: participant_registration
id: shinka
repository: <org>/arena-participants
manifest: shinka/arena.yaml
track: main
update_policy: validate_new_versions
recommended_commit: <full-commit-sha>
visibility: team

Ветка нужна для обнаружения обновлений. RunSpec фиксирует полный SHA и image digest; новый commit не меняет запущенный эксперимент.

04 / UML Class diagram

Три контракта расширения

Новый участник реализует эти интерфейсы. Общий алгоритм поколений в Arena не появляется.

1. Task package

Manifest объявляет задачи, формат кандидата, seed, evaluator entrypoint, метрику и min/max, данные, seeds/повторения, CPU/GPU и окружение. Search feedback и final evaluation определяются протоколом задачи.

2. Participant package

Manifest объявляет image, entrypoint, схему настроек, совместимые protocols и checkpoint/resume capabilities. Arena передаёт RunSpec, workspace и ограниченные endpoints. Adapter запускает родной процесс и переводит его журнал в общие события.

3. Evaluation API

evaluate(candidate_ref, profile, request_id) передаёт точный пакет программы. Arena назначает условия и возвращает receipt: статус, validity, raw metric, fitness mapping, расходы и артефакты. Повторная доставка запроса не создаёт новую оценку; новое измерение получает новый ID.

ОбъектСоставНазначение
VersionLockRepository ID + commit, manifest hash, upstream locks, image digest + platform, data/protocol hashes.Закрепляет исходники и полное окружение.
RunSpecTaskVersion, ParticipantVersion, модели, seeds, hardware profile, лимиты и feedback policy.Неизменяемые условия эксперимента.
RunAttemptWorker identity, lease epoch, checkpoint и причина остановки.Разделяет логический run и попытки его исполнения.
EvaluationReceiptCandidate hash, inputs/outputs, metric/direction, validity, ресурсы и provenance.Основание официального результата.
DGM регистрируется как участник, но не становится совместимым со всеми задачами. Его native candidate — версия агента. Для задач, принимающих программу, нужен episode adapter: агент решает задачу и выдаёт программу evaluator. Сначала frozen agent, затем outer evolution. В истории раздельны agent revision, episode и candidate; все вложенные расходы учитываются.

Если задача принимает agent bundle, это отдельный protocol. Если принимает Python-программу, подключение должно выдавать именно её. Борда разрешает запуск по совпадению capabilities задачи и участника.

05 / UML Sequence + State diagrams

Запуск, фиксация результата и восстановление

Борда создаёт запись в Cloudflare. Supervisor на Vast забирает её по pull-протоколу. Изменения состояния связаны с attempt_id и текущим lease_epoch.

Правила отказоустойчивости

СобытиеПоведение
Повтор POST /runsIdempotency key возвращает существующий run. Второй процесс не создаётся.
Повтор событийДедупликация по (attempt_id, sequence); расходы не учитываются дважды.
Нет heartbeatOrphaned → reconciling. Не повторяем потенциально живую платную работу автоматически.
StopСохраняем cancel intent. Worker прекращает новые действия, завершает/отменяет текущие, выгружает checkpoint и подтверждает итог.
ResumeТолько по capabilities и совместимому checkpoint. Новый epoch блокирует публикацию актуального состояния старой попыткой.
Неизвестный LLM outcomeРезерв остаётся до сверки. Idempotency доставки не обещает exactly-once внешних эффектов.
UML состояний запуска

Полный учёт ресурсов

USD, wall time, CPU/GPU и число проверок — отдельные лимиты. Gateway считает generation, research, embeddings и evaluator LLM. Native billing используется для сверки, а не повторного сложения.

Условия сравнения

Совпадают task/protocol version и ресурсные условия. Неизвестные расходы видны явно. У DGM раздельно показываем развитие агента и решение задач; стоимость outer loop не исчезает.

06 / Architecture decisions + delivery gates

Решения и порядок реализации

Задано тобой

Самостоятельная Arena

Задачи, окружения и борда принадлежат платформе. Фреймворки — подключаемые участники.

Подтверждено

Команда + PR-реестр

Закрытая v1. Платные запуски доступны команде. Merge и webhook сами не запускают исследование.

Предлагаю · ADR-01

Репозиторий платформы Arena

Board, API, worker, schemas и registry/ вместе. Репозитории задач и участников независимы.

Предлагаю · ADR-02

Workers + D1 + R2; Vast pull

Одна VM и очередь в D1. Queues/DO и автоматический флот вводим при потребности в масштабе.

Предлагаю · ADR-03

Arena собирает пакеты

Закреплённый source → ограниченная build job → conformance → доступная версия. Builds тоже имеют бюджет.

Предлагаю · ADR-04

Native process contract

Launcher + telemetry adapter. Arena не навязывает общий step/propose цикл и стратегию поиска.

План с критериями готовности

  1. Выделить Arena и закрепить контракты

    Структура проекта, task/participant schemas, RunSpec, registry и отделение UI от Engine.

    Приёмка: сервер Arena работает без SCiEL; старый run отображается через reader.

  2. GitHub → каталог → окружения

    GitHub App, подписанный webhook, durable inbox, immutable locks, build/conformance. Текущий task repo подключён как коллекция.

    Приёмка: merge PR добавляет версию; невалидный manifest отклоняется; текущие runs не меняются.

  3. Cloudflare + Vast и первый участник SCiEL

    Team auth, D1 lease, R2 uploads, supervisor, evaluator, gateway и SCiEL adapter.

    Приёмка: проходят контрольный кандидат, Stop, повтор API и потеря heartbeat.

  4. ShinkaEvolve и общий Compare

    Второй adapter, общий RunView, сравнение и дополнительные native views.

    Приёмка: два независимых поиска на одном task protocol; каждая точка ведёт к коду, receipt и расходам.

  5. DGM через эпизоды

    Frozen agent, затем outer evolution, lineage и разделение development/final evaluation.

    Приёмка: видно, какой агент создал решение и сколько стоила вся вложенная работа.

Следующие архитектурные решения

ВопросРекомендуемый стартУсловие пересмотра
Build infrastructureИзолированная job из pinned source.Тяжёлые GPU builds: отдельная машина или доверенные prebuilt images с provenance.
Compute fleetОдна VM с явными ресурсными слотами.Устойчивая очередь: provisioning через Vast API и несколько worker profiles.
Final evaluationСледуем протоколу задачи; показываем, есть ли независимая проверка.Для новых benchmark-результатов вводим закрытый final split как новую версию протокола.
Конкретные изменения в SCiEL adapter
  • Запускать актуальный полный Engine. Старый launcher task repo использует OpenEvolve и ограниченный SCiEL-профиль.
  • Разделить raw loss и максимизируемый fitness; исправить refinement и score bins для отрицательных значений.
  • Не дублировать дорогое измерение через smoke/full. Новая репликация получает новый ID и учитывается отдельно.
  • Сохранять generic scientific artifacts. Открытие борды не запускает повторных вычислений.

RFC 02 заменяет предыдущую схему интеграции. Архитектура и manifest-примеры — предложения; реализация и облачные ресурсы не создавались.
